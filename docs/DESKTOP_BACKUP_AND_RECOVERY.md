# MyFinHub — Windows local finance backup and full Production recovery

Owner approval 2026-10-24 · Issue #619 · Integration baseline `develop`. Android repository is out of scope.

## Two independent recovery boundaries

### Installed Windows application: no setup scripts
- The installer bundles `desktop/backup-store.cjs` (never Supabase admin credentials).
- The first **installed launch** creates a user-owned backup folder at the operating-system Documents location `MyFinHub/Backups`, plus the versioned `backup-index.json` catalog. This is **local backup storage**, not a second finance database or an automatically created Supabase instance.
- Owner can select another location through **Settings → Data → Automatic local Windows backups → Change folder**. Previously written files stay in the prior folder; they are not silently removed/copied.
- After the authenticated owner+AAL2 finance app has loaded and database saves are idle/successful, the Windows runtime checks the most recent verified backup. It reads a fresh server-authoritative `GET /api/data` and writes one JSON snapshot whenever the most recent valid local snapshot is at least 24 hours old. Checks repeat hourly **while the application remains open and authenticated**. Closing Windows MyFinHub or losing auth means no scheduled backup, not a false background service.
- Each snapshot is fetched **inside Electron main** from the authenticated owner+AAL2 /api/data endpoint (no renderer-supplied financial payload is trusted), size-bounded (4 MiB), atomically written, reopened, SHA-256 verified and listed with revision/date/integrity. Filename is program-generated; no renderer-chosen target path is accepted.
- Retention: preserve at least the newest backup, otherwise files within 30 days up to 45 records. Only files named/generated by this service are deleted during retention. The index is written atomically. A damaged file is marked invalid and refused for restore.
- **Manual Backup & λήψη** retains the existing owner+AAL2 server-side backup and browser JSON download; on Windows it additionally writes and checks a local snapshot from a fresh `GET /api/data`. If local write fails, show partial success, not a false all-green message.
- Clicking a listed **Restore** first verifies the stored checksum then passes the JSON through the existing explicit destructive import confirmation; owner+AAL2, database revision/history/audit, pre-import backup and irreversible import semantics remain unchanged.
- Plain finance JSON is allowed by the owner's preference; Windows file permissions/storage safety still matter. The backups intentionally do **not** contain PAN/CVV/expiry secrets, card-vault key/ciphertext, independent IBAN material, uploaded Supabase Storage objects, device-local receipts, PIN or production credentials. Protect the selected folder from other Windows users.

### PostgreSQL database recovery and deployment
- The **canonical single-owner finance database remains hosted on Supabase**. Installing the desktop application cannot safely create/migrate a new *production* Supabase database: that would require privileged credentials and undermine the centrally shared finance/revision/RLS contract. First-launch initialization is only the local backup catalog.
- Local application JSON is for owner finance-data import; it is **not** a full PostgreSQL disaster recovery image (schema, roles, migrations, audit/retained history, vault and Storage binaries).
- Before Production schema migrations, the release operator must create a verified current PostgreSQL dump and isolated test restore using secure offline credentials, plus separately protect required Storage objects and key recovery material. No database password/service-role key belongs inside Electron/renderer/browser, GitHub artifacts or a PR comment.
- Supabase Free has no automated Pro daily backups; the operator backup prerequisite remains unresolved on PR #605 until evidence is supplied. **Do not mark a Desktop finance snapshot as satisfying the Production migration recovery gate.** It does not.
- Schema is initialized or upgraded only by ordered, reviewed `supabase/migrations` during separately authorized infrastructure deployment. Automatic schema creation in a newly installed personal Windows client is explicitly unsupported for security and single-source-of-truth reasons.
