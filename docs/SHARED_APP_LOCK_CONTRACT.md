# MyFinHub shared application privacy lock (draft #622)

## Scope and security boundary
- A four-digit owner-selected PIN is shared by the Web and Windows clients through the same authenticated server API. This does **not** replace Supabase Auth, mandatory TOTP, owner UID, AAL2, current-device revocation or RLS. It must never authorize access to those boundaries by itself.
- The app privacy lock prevents unattended access in three layers: the React finance tree is unmounted, the application API requires a valid per-session memory-only unlock token on finance/device/account routes, and the forward-only database migration adds a live-ticket check to the canonical owner+AAL2+active-device finance RLS predicate. Removing or hiding the PIN modal is not authorization. This mechanism is **unreleased and unvalidated on a real isolated database**; do not describe it as deployed security.
- The PIN is never stored in browser localStorage/IndexedDB or returned by the API. The DB table and verifier have no authenticated grants; a narrowly scoped SECURITY DEFINER RPC compares a bcrypt verifier after strict owner+AAL2+active-device checks, with database-shared failed-attempt throttling. Only a random 256-bit session-bound unlock token is returned after success; its hash is stored in RLS-protected private data and expires at the configured inactivity interval. Valid activity renews its short lease. Locking one tab revokes the session's tickets. Never expose the PIN hash to client access.
- Both Web and Windows show a PIN gate on a fresh authenticated page opening when shared PIN is enabled. On inactivity the UI locks, and after a backgrounded tab resumes past timeout it locks. The normal web login/TOTP flow remains available when there is no authenticated session.
- Windows legacy DPAPI PIN is retained and used only if the global PIN is not configured. The old PIN is not silently uploaded to the server, and enabling the global PIN is an explicit owner action. Remove/retire the legacy fallback only after an accepted migration policy.
- A high-assurance lost-PIN recovery flow is implemented in source, but **not validated or released**. From the locked UI, the owner must supply a fresh account password, a new TOTP challenge response and a confirmed replacement PIN. The server authenticates separately through GoTrue, never copies the temporary token into existing HttpOnly cookies, and the DB recovery RPC requires both signed `amr` password + TOTP timestamps within 120 seconds. Ordinary ambient AAL2 does not meet this freshness test. Temporary GoTrue sessions are terminated with explicit `scope=local`, never the default global logout, so other Web/Windows/Android sessions are not revoked. A successful reset invalidates old unlock tickets and requires ordinary PIN verification to obtain a new token. This path still requires real-stack recovery/negative tests before release.

## Owner-facing configuration
Settings → Χρήστης & Πρόσβαση → PIN & αυτόματο κλείδωμα. Choices: 1, 5, 15, 30, 60 minutes (default 5); configuring a new global PIN requires confirmation. Changing, disabling, and updating the timeout require the current PIN. A forced "Κλείδωμα τώρα" event locks on the same client.

## API contract (Web, desktop, future Android)
All requests use the existing authenticated owner session with AAL2/current-device policy and publishable key; browser routes use same-origin cookies, same-origin mutation guard. No service-role key.
- `GET /api/auth/app-lock` → `{ok:true,enabled:boolean,idleMinutes:number,retryAfterMs:number}`.
- `POST /api/auth/app-lock`, JSON `{action:'configure',newPin:'1234',idleMinutes:5}` (when unset), `{action:'verify',pin:'1234'}`, `{action:'change',pin:'1234',newPin:'2345'}`, `{action:'timeout',pin:'1234',idleMinutes:15}`, `{action:'disable',pin:'1234'}`. Failed verification is a 200 JSON `ok:false,error:'APP_LOCK_WRONG_PIN'|'APP_LOCK_RATE_LIMITED',retryAfterMs` so UI can count down; upstream/security transport errors are HTTP errors and must fail closed.
- PIN values have exactly four ASCII digits; idle timeout accepts the five canonical choices. Never log request PINs or include them in telemetry.
- `POST /api/auth/app-lock` action `recover` with `{email,password,code,newPin}` uses a separate fresh password+TOTP GoTrue session. The server invokes a narrowly scoped database recovery RPC with only the freshly MFA-verified JWT. Password and code are not logged; the existing session is not replaced or globally logged out. Do not activate until isolated RLS and GoTrue AMR tests pass.
- The PIN endpoint explicitly supports an owner+AAL2/active-device native bearer request (with no cookie fallback), and native finance bearer requests **also require** a live unlock token when shared PIN is enabled. This closes the cookie-to-bearer DevTools bypass. Because Android is a separate product repository and has not yet integrated the ticket contract, **shared PIN MUST NOT be activated in production until Android compatibility is implemented and validated**. No client platform/UA header may exempt an API from PIN enforcement.

## Device registry additions
`GET /api/auth/devices` returns optional `nickname`, `defaultLabel`, `systemName`, `browserName`, `deviceType`, existing platform/version/firstSeenAt/lastSeenAt/current. System and browser labels are coarse client/UA-reported hints, not verified hardware identity, and never include raw IP/user-agent. `POST /api/auth/devices` `{action:'rename',sessionId:'<canonical-UUID>',nickname:'My Laptop'}` updates an active owner's nickname; empty string clears it. Nicknames are not rewritten by normal device heartbeat or platform updates.

## Validation and release
Migrations `20261024150000` (device metadata) and `20261024160000` (shared PIN) are forward-only and require pre-deployment migration verification. Narrow unit/source checks, live database RPC/RLS/lockout race checks, rendered mobile/desktop QA, native Windows packaging and full exact-head CI are required. Do not merge/deploy this draft until these pass; keep unrelated financial history and Android source intact.

## DevTools threat model and evidence boundaries (owner direction 2026-10-24)
- The owner explicitly requires a modern, consistent Light/Dark and mobile PIN screen with polished micro-interactions, keyboard/paste input, idle/retry/error/busy/success states, reduced-motion support and direct screenshot/interaction acceptance.
- Removing an overlay or editing React state via DevTools does **not** create a valid backend ticket. Unauthorized cookie or bearer API requests must fail with `423 APP_LOCK_REQUIRED`. The Supabase RLS extension must independently deny finance access from a copied AAL2 JWT when the session has no live PIN ticket; this requires real-database end-to-end proof, not source assertions.
- A person who fully controls an **already unlocked** browser, its JS execution environment, memory and debugging tools could capture a currently valid token or read already rendered information. No client-side modal can guarantee prevention against this privileged attacker. Minimize such exposure with short server-bound tickets and immediate server invalidation on lock. Windows OS-session locking and browser/device access controls remain necessary.
- New password→MFA completion must re-run the PIN gate before finance data can render. API and RLS token checks are fail-closed on upstream errors; no credential- or token-value logging.
- QA must capture Light/Dark, mobile/desktop, loading, valid, wrong PIN, rate-limit, explicit lock, idle timeout, background resume, focus, paste, reduced motion and DevTools-style modal removal/direct API forgery. No PASS until actual artifacts are inspected.
