# PostgreSQL + Supabase Storage independent checkpoint and recovery

**Status: isolated local rehearsal, NOT production restore authorization.** Owner approval and secure infrastructure credentials are required before any production backup/restore. Finance JSON backups and Windows desktop snapshots are **not** full disaster-recovery images.

## Required scope

An independently recoverable PostgreSQL+Storage checkpoint must pair a **consistent** PostgreSQL archive (schema, finance ledger, history, backups, audit, owner authorization, device sessions, auth state, metadata, migration ledger and RLS) with **every** referenced Supabase Storage binary (not merely `storage.objects` metadata). Include an integrity manifest with SHA-256 hashes, storage bucket/key, object content type, creation timestamp, application/database version and archive hash. Also safeguard separate encryption/recovery keys in an approved secret store, never inside the checkpoint artifact or GitHub logs.

A checkpoint is **not accepted** if Storage bytes are missing, if an archive hash differs, if PostgreSQL changes while Storage capture is in progress without a documented consistency boundary, or if either component cannot be restored into a **different isolated recovery environment**. Do not remove or rewrite original rows, audit, backup history or stored objects when rehearsing a restore.

## Disposable automated proof

The CI-only `npm run qa:isolated-recovery` command explicitly checks `CI=true` and `MYFINHUB_ISOLATED_RECOVERY=1`, verifies the exact running Docker container `supabase_db_rheomiq` and a loopback-only local Supabase Storage API, then:

1. Captures finance/backup/audit, auth, Storage metadata and migration checksums from synthetic **local** state; produces a PostgreSQL custom archive, copies it outside the database container and verifies its SHA-256 on transfer.
2. Creates a temporary private local source bucket with a genuine synthetic Storage binary so the proof is non-vacuous even when other test objects have already been cleaned up. Takes **all** local Storage objects into a separate temporary directory, saves per-object checksums and rejects incomplete/oversized snapshots. Downloads private objects through `/storage/v1/object/authenticated/<bucket>/<path>`.
3. Restores the archive into a newly created **scratch PostgreSQL database** from `template0`. It preserves the template-provided empty `public` namespace, which `pg_dump` does not recreate when it is the unmodified default schema. Supabase's `postgres` role is intentionally not a superuser: a preflight confirms the internal **local Docker-only** `supabase_admin` can connect and is a superuser before using it solely for the isolated `pg_restore --exit-on-error`. This is needed for unmodified Supabase Realtime function definitions that set protected `log_min_messages`. The harness does **not** elevate the source database's `postgres` role, copy source rows into scratch, or use admin credentials on production. It verifies selected canonical row hashes, migration history and enabled RLS topology against the untouched original.
4. Uploads recovered binary assets into an isolated, temporary local Storage bucket, downloads them again and compares all SHA-256 hashes before removing that namespace.
5. Deletes both isolated Storage fixture buckets (source and restored copy), compares the original PostgreSQL/Storage metadata hashes with the baseline from before fixture creation, and removes the scratch database and temporary checkpoint bytes. The disposable local Supabase service is stopped without backup by CI. The isolated proof runs **after authenticated API finance/Storage tests but before the browser stage**, so a Chromium hang cannot hide its separate result.

This proof does **not** restore Supabase global roles into a distinct physical cluster or reproduce production secrets, provider encryption material, project-level configuration, external auth/Storage infrastructure and point-in-time consistency across a live writing system. Even a successful local run therefore does **not** by itself close an owner production recovery/release gate.

## Read-only artwork orphan inventory (I19.04)

`scripts/recovery-fixtures/artwork-storage-inventory.sql` is an offline **metadata-only** inspection for an authorized operator on a consistent isolated PostgreSQL+Storage checkpoint. It uses a repeatable-read read-only transaction and `row_security = off` (which fails rather than silently returning RLS-filtered rows when the executing role cannot see all relevant rows). Do not run it through the browser, native client, public RPC, or an ordinary owner JWT. Do not connect it to hosted production without separate owner-approved operational access. The output contains bucket/path identities and must stay in the protected operator workspace, not logs, Git or public artifacts.

It compares exact bucket/path pairs across Storage metadata and both artwork registries, **including inactive rows**. The report distinguishes registered-active, registered-inactive, storage-only-unregistered, registry-only-missing-object and ambiguous-identity; it also counts incomplete provider Storage pointers. Legacy provider rows with neither Storage pointer are outside this inventory. A Storage metadata row alone does not establish the actual binary exists or its hash matches.

The separate `recurringReferences` list starts from canonical reference keys rather than Storage objects. It reports current (including relational), retained history and backup reference flags alongside registry, active-registry and metadata object counts, so a historical key absent from both registry and Storage remains visible. `providerReferences` covers current slot bindings and legacy logo/wordmark pointers, including inactive records; a zero registered-object count can also describe legacy non-Storage artwork, not necessarily a lost image. No raw FinanceData, backup/history payload or financial values are returned. The rehearsal uses the exact two synthetic recurring artwork identities removed earlier through the normal authenticated lifecycle, requires retained history reference evidence and zero current/registry/object counts, and includes history points and cursor in the restore fingerprints. This diagnostic intentionally does not alter Undo/Redo or retention semantics; external/exported backups and noncanonical references still require separate review.

A storage-only candidate is **not deletion authorization**. It may represent an in-flight or lost-receipt upload, another writer, old references, or an inconsistent snapshot. Before any separately approved recovery action, stop/coordinate writers, verify actual object bytes and a consistent checkpoint, review current finance and provider bindings plus retained history/backups and all other references, and resolve duplicate or incomplete identities. Preserve unknown objects and missing references until reviewed; never remove Storage metadata via SQL, never issue automated orphan purges, and never rewrite finance/history to reconcile artwork. Use the supported Storage API only for explicitly approved exact-object operations. This is an inventory and triage boundary, not a durable upload idempotency or cross-tab recovery protocol.

The isolated CI rehearsal creates two uniquely named synthetic unregistered SVG objects (one per application artwork bucket), verifies their real metadata classification, includes them in the existing independent archive and SHA-256 byte replay, compares the restored inventory to source, then removes only the two known fixture paths and verifies the original inventory is unchanged. The inventory itself has no mutation capability and logs only the pass marker, never the report. See Supabase's [Storage schema documentation](https://supabase.com/docs/guides/storage/schema/design) for the read-only metadata boundary.

## Durable artwork upload reservation foundation (release-pending)

The forward-only `20261125090000_add_artwork_upload_intents.sql` migration introduces an owner+AAL2/active-session protected reservation journal. Each explicit upload has a unique intent UUID and a separate unique generated artwork key, an exact target (provider/role/variant or recurring ID), canonical Storage path, MIME, byte count and SHA-256 fingerprint. The pending-only unique index arbitrates the target across server instances and browser restarts. The journal contains no binary or auth token; filename and target are private owner metadata. Terminal rows remain as key tombstones: no authenticated DELETE, identity mutation or reopening. The same file bytes/name are never an intent identity. Dispositions describe acknowledgement or deliberate abandonment; they are not evidence of Storage bytes, registry state, finance revision or authorization to mutate other stores.

This checkpoint is the **schema foundation only**, not an active upload/recovery protocol. Before runtime integration, verify the ordinary disposable PostgreSQL smoke (independent owner session, pending-slot uniqueness, independent slots, terminal identity retention, negative owner AAL1/nonowner AAL2/revoked owner AAL2 and grant boundaries). The isolated full-recovery fingerprint includes the journal so a restored checkpoint cannot silently discard unresolved reservations or terminal key tombstones. Subsequent runtime work must reserve before any Storage POST, never continue after an ambiguous reservation without exact authoritative reconciliation, never automatically replay an existing intent, verify exact active registry and object bytes before any successful recovery acknowledgement, and provide explicit review for unresolved/abandoned intents without deleting objects or rewriting history. Normal legacy native request/response compatibility must be preserved; no Android code changed. No production migration has been applied.

## Production operator protocol (approval-gated, not executed by this repository)

1. Obtain explicit owner approval for an offline **backup** and a separate approval for any production-changing **restore**. Identify the exact project, maintenance/change window, recovery-point and retention objectives, and enforce least-privilege access.
2. Stop or coordinate all writers for a consistent PostgreSQL+Storage snapshot, or use a reviewed versioned manifest/object-generation capture scheme. Record the database revision, schema-migration ledger, app version, object hashes and encrypted archive location. Store all binary objects in separately protected/offsite Storage that does not depend on the original project surviving.
3. Keep PostgreSQL credentials, service-role secrets, MFA recovery and Card Vault key material **out of source control, artifacts and client binaries**. Encrypt the checkpoint at rest and restrict access to the owner/operator.
4. Restore into a distinct, isolated **non-production** Supabase environment. Recreate platform roles/extensions/project configuration using the provider-supported recovery procedure, restore database and Storage binaries, verify every manifest entry, RLS/owner+AAL2, canonical ledger/history/audit, private object permissions, media links, health checks and checksum integrity. Compare the final migration ledger before any application cutover.
5. Require explicit recorded go/no-go after successful independent restore, verified provenance and a rollback path. Never equate a FinanceData JSON import, a schema roll-forward smoke or a local backup catalog with this full recovery process. Do not use destructive database reset, truncate or live production overwrites to test a checkpoint.

**I18.02 remaining boundary:** The local PostgreSQL scratch-database + separate-bucket rehearsal is valuable non-destructive evidence but is not the independently hosted and keyed production-grade restore. Actual full production-equivalent recovery requires a distinct isolated Supabase project/cluster and operator-approved secure credentials/evidence; no such production action is requested or performed here.
